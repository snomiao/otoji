# 03 — LLM Polish レイヤ

ASR の生出力 (raw transcript) には次のような問題が残ります:

- 句読点・改行が無い、もしくは過剰
- 数字・単位・日時が音声どおりで正規化されていない (例: 「ニーゼロニーロクネン」→「2026 年」)
- フィラー (「えーと」「那个」) がそのまま入る
- 固有名詞・専門用語が誤変換される
- 文境界が曖昧で検索/要約に流せない

これを解決するのが **LLM polish レイヤ**です。

## アーキテクチャ

```mermaid
flowchart LR
    Mic[Browser Mic] --> PCM[PCM 16k mono]
    PCM --> ASR[RT ASR\n(RTASR / CoLi / SenseVoice)]
    ASR -- partial --> UI1[UI: gray italic]
    ASR -- final segment --> Buf[Sentence Buffer]
    Buf -- 2〜5s 沈黙 or 句末 --> LLM[LLM Polish]
    LLM --> UI2[UI: black confirmed]
    LLM --> Store[(Transcript Store)]
```

ポイントは **二層 UI** にすること:

1. ASR の partial をそのまま薄字でストリーム表示 (体感レイテンシ最優先)
2. LLM が整形した確定版を上書き (品質優先)

## トリガ戦略

| トリガ | 説明 | 向き |
|---|---|---|
| 句末確定 (`type=0`) | iFlytek 系 / CoLi で `seg_id` が確定したタイミング | 低レイテンシ重視 |
| 沈黙検出 (VAD 200ms 以上) | 話の切れ目 | 自然な文単位 |
| N トークン蓄積 | 例: 60 文字超 | 暴走防止 |
| 固定タイマ (例: 3s) | 上記いずれも来ない場合の保険 | 会議書き起こし |

実用上は **「句末確定 OR 3 秒タイマ」** の併用が無難です。

## プロンプト設計 (例)

```text
あなたは ASR 出力の整形係です。以下の制約で書き直してください。
- 意味は変えない。要約しない。
- 句読点と改行を補い、フィラー (えーと/那个/um) を削除する。
- 数字・日時・単位は表記揺れを正規化する。
- 中英混在はそのまま維持する。
- 固有名詞辞書: {{glossary}}
- 直前 1 文の文脈: {{prev_sentence}}

入力:
{{raw_segment}}

出力 (整形後の本文のみ):
```

## モデル選定

| モデル | レイテンシ (1 文) | コスト | 中文 | 用途 |
|---|---|---|---|---|
| Claude Haiku 4.5 | ~400ms | 低 | ◎ | 既定の polish エンジン |
| Claude Sonnet 4.6 | ~700ms | 中 | ◎ | 議事録・要約と兼用するとき |
| GPT-4o-mini | ~500ms | 低 | ◯ | フォールバック |
| Qwen2.5-7B (ローカル) | ~300ms (GPU) | GPU 償却 | ◎ | セルフホストで固定費化 |

SenseVoice をセルフホストするなら、polish も Qwen2.5 系で揃えると 1 台の GPU ノードに収まります。

## ストリーム整形のテクニック

- **差分パッチ送信**: polish 結果は文単位なので、`{segId, text}` で UI に反映する。partial を全文置換しない。
- **再順序対策**: ASR が後から `seg_id=N` を訂正してきた場合、polish 済みの該当文も再生成する。
- **辞書注入**: `glossary` を会話開始時に固定し、毎リクエストで前置するだけで固有名詞精度がかなり改善する。
- **コスト制御**: polish は文単位 = 1 リクエスト 100〜200 トークン程度。1 時間の会議でも数十円〜数百円。

## 評価指標

- **CER / WER** (生 ASR vs polish 後 vs 人間正解)
- **句読点 F1**
- **End-to-end latency**: マイク入力から polish 後表示まで p50 / p95
- **コスト/分**: ASR + LLM の合算
